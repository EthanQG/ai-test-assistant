# 电商订单履约与优惠结算需求 PRD

## 1. 项目背景

商城目前的下单、库存扣减、优惠券核销和支付结果处理分别由不同服务完成。活动期间出现过重复下单、优惠券重复使用、支付成功但订单未更新、库存被重复扣减等问题。本期需要统一订单创建与履约规则，为后续促销活动提供稳定能力。

## 2. 目标与范围

本期支持普通实物商品订单，覆盖购物车结算、库存校验、优惠券使用、订单创建、支付、取消和超时关闭。

本期不支持预售商品、虚拟商品、跨境商品、积分抵扣、会员折扣和多张优惠券叠加。

## 3. 用户与权限

1. 用户必须登录后才能提交订单。
2. 用户只能查看、支付和取消自己的订单。
3. 客服可以查询订单和查看状态流转记录，但不能代替用户支付。
4. 运营管理员可以人工关闭“待支付”订单，操作时必须填写原因并记录操作人和时间。

## 4. 购物车与结算

1. 用户可以勾选一个或多个商品SKU进入结算页。
2. 结算页展示商品名称、SKU属性、购买数量、商品单价、商品金额、优惠金额、运费和应付金额。
3. 商品金额等于各SKU成交单价乘以数量后的合计。
4. 应付金额等于商品金额减优惠金额再加运费，最低为0.01元。
5. 用户提交订单时，系统必须重新校验商品状态、购买数量、价格、库存和优惠券有效性，不能直接使用进入结算页时的旧结果。
6. 单个SKU每单最多购买99件，最少购买1件。
7. 不同店铺的商品不能合并为同一张订单。

## 5. 库存规则

1. 库存以SKU维度管理。
2. 提交订单时，只有所有SKU可售库存均大于或等于购买数量，才允许创建订单。
3. 库存不足时，订单创建失败，并向用户提示“部分商品库存不足，请返回购物车修改数量”。
4. 创建订单成功后立即锁定库存；支付成功后将锁定库存转为已售库存。
5. 待支付订单被用户取消、运营关闭或超时关闭时，应释放已锁定库存。
6. 同一个用户连续提交相同购物车时，客户端必须携带唯一`request_id`。服务端应保证同一个`request_id`只创建一张有效订单，库存只锁定一次。
7. 库存锁定成功但订单保存失败时，不允许留下无法关联订单的长期锁定库存。

## 6. 优惠券规则

本期支持“满200元减30元”的平台优惠券：

1. 门槛只计算商品金额，不包含运费。
2. 商品金额达到200元时可用，199.99元不可用。
3. 每张订单最多使用一张优惠券。
4. 优惠券必须属于当前用户，且在有效期内、状态为“未使用”。
5. 提交订单成功后，优惠券状态变为“已锁定”；支付成功后变为“已使用”。
6. 订单创建失败时不得锁定优惠券。
7. 待支付订单取消或关闭时触发优惠券退回，但优惠券在退回时已经过期应如何处理，本期需求暂未明确。
8. 已支付订单发生退款时，本期不自动退回优惠券。

## 7. 订单创建

1. 订单号由系统生成并全局唯一。
2. 订单创建成功后的初始状态为“待支付”。
3. 创建成功后记录订单商品快照、价格快照、优惠券信息、运费、应付金额、用户ID、店铺ID和`request_id`。
4. 商品价格、库存或优惠券校验失败时，不得生成有效订单，也不得锁定库存和优惠券。
5. 订单创建接口整体响应目标为3秒以内；超过3秒时前端展示“订单正在处理中，请勿重复提交”，随后可以根据`request_id`查询处理结果。
6. 对于服务端处理超时后客户端重试的情况，仍必须遵守同一`request_id`只创建一张有效订单的规则。

## 8. 支付与回调

1. 待支付订单允许发起支付，支付金额必须与订单应付金额一致。
2. 支付成功回调必须记录支付平台流水号、支付时间和回调接收时间，并将订单改为“已支付”。
3. 同一支付流水号的重复成功回调不得重复记账、重复扣减或重复变更库存。
4. 已取消或已关闭订单收到支付成功回调时，不得直接恢复为“已支付”，应记录异常并进入人工处理队列。
5. 回调签名校验失败时不得更新订单和记账。
6. 支付回调失败后的重试次数、重试间隔和最终告警方式，本期需求暂未明确。
7. 支付成功后，如果订单状态更新失败，系统必须保留支付流水和失败记录，支持后续核对与补偿；具体自动补偿策略暂未明确。

## 9. 取消与超时关闭

1. 用户只能取消“待支付”订单。
2. 已支付、已发货、已完成和已关闭订单不能由用户取消。
3. 用户取消时需二次确认，取消成功后状态变为“已关闭”，并释放库存及触发优惠券退回。
4. 待支付订单创建30分钟后仍未支付，应自动关闭。
5. 支付操作与自动关闭同时发生时，应确保订单不会同时表现为已支付和已关闭；最终优先规则暂未明确。
6. 重复取消同一订单不得重复释放库存或重复退回优惠券。

## 10. 状态流转

允许的主要状态流转如下：

- 待支付 → 已支付
- 待支付 → 已关闭
- 已支付 → 待发货
- 待发货 → 已发货
- 已发货 → 已完成

不允许从“已关闭”恢复到“待支付”。任何状态变更都应记录变更前状态、变更后状态、触发来源、操作人或系统任务标识及时间。

## 11. 异常提示与记录

1. 库存不足、优惠券不可用、商品失效和价格变化必须向用户展示可理解的业务提示。
2. 系统内部异常不得直接向用户展示堆栈、数据库信息或第三方支付错误原文。
3. 订单创建、库存锁定、优惠券锁定、支付回调和订单关闭均需记录业务日志，并可通过订单号或`request_id`查询。
4. 对重复请求、重复支付回调和重复取消，应记录幂等命中信息。

## 12. 非功能要求

1. 活动高峰预计每秒最多500次提交订单请求。
2. 任一用户不得查看或操作其他用户订单。
3. 金额计算统一保留两位小数，不使用浮点数进行财务计算。
4. 关键状态和资金相关日志至少保留180天。
5. 系统局部依赖不可用时应明确失败或进入可恢复状态，不能向用户返回成功后静默丢失订单。

## 13. 验收重点

1. 正常订单能够完成创建、支付及库存状态转换。
2. 199.99元、200元门槛及含运费后超过200元的优惠券边界正确。
3. 库存恰好等于购买数量时允许下单，少于购买数量时拒绝。
4. 相同`request_id`串行或并发提交只生成一张有效订单。
5. 重复支付回调、重复取消不会产生重复记账、库存释放或优惠券退回。
6. 支付与关闭并发时不存在互相冲突的最终状态。
7. 用户、客服和运营管理员的权限符合要求，越权访问被拒绝并记录。
