## 当前阶段

阶段 2.11.4：Agent执行体验与人工反馈稳定性优化。

已完成：

- 执行下一个节点前先由Orchestrator计算动作，页面显示具体中文节点名
- LLM节点明确提示通常需要1–2分钟，避免同步等待被误判为页面死锁
- 知识检索明确说明外部服务失败时会记录降级并继续
- `OrchestratorDecision`新增`duration_seconds`，记录节点实际执行耗时
- 决策轨迹使用中文动作并展示耗时
- 用户补充信息后的需求重新分析同样记录决策与耗时
- 人工反馈提交成功后显示受理提示
- 人工反馈组件使用递增版本键重建，处理完成后不会保留旧内容
- 运行期间反馈入口消失，结合已有`in_progress`保护降低重复执行风险
- 真实回归发现12个测试点的整集合修正即使使用8192 token仍会截断
- Reviser改为只返回`add`、`replace`、`remove`操作，由Python严格校验并原子应用
- 未修改测试点不再由LLM重复输出，人工新增业务规则的修正响应显著缩短
- 决策和事件轨迹改用静态表格，避免动态DataFrame连续刷新触发React #185
- 静态轨迹由安全转义的HTML生成，不显示Streamlit默认索引列
- Agent事件表显式增加业务序号列，不依赖组件自动生成的DataFrame索引
- 同一节点执行中不再每秒轮询重跑，也不再同时渲染重复的info与spinner组件
- Reviewer将`missing_scenarios`和`revision_suggestions`中的纯空白字符串过滤掉，兼容模型返回`[""]`的等价空结果
- Reviewer Prompt明确要求无问题时返回真正的`[]`，不得使用空字符串或占位文字
- 人工反馈触发Reviser时不再携带已通过的旧Reviewer意见，避免模型扩大修正范围
- 人工反馈按照动作限制允许的增量操作：新增最多3项，删除、修改和优先级调整通常最多1项
- 操作数量或类型越界会进入结构化重试；仍不合规时整次修正失败且不改变原测试点

执行体验边界：

```text
执行前：显示“正在执行：具体节点”与等待预期
执行中：Streamlit同步等待，不能实时更新秒数
执行后：记录实际耗时并刷新决策、事件和结果
```

## 测试基线


已额外使用 Streamlit AppTest 验证：

- LLM节点进度提示包含具体节点、等待预期和防重复说明
- Orchestrator使用受控时钟测试记录节点耗时
- Presenter将决策动作转成中文并格式化耗时
- 提交业务规则反馈后表单版本递增、反馈只保存一条且显示受理提示
- 增量修正支持增加、替换、删除，并保留未修改测试点
- 任一操作目标无效时整次修正失败且原测试点不变
- 执行轨迹使用静态表格，`in_progress`任务不会启动重复轮询
- 静态表格无默认索引列，并对模型内容进行HTML转义
- Agent事件显式展示从1开始的业务序号
- Reviewer可选问题列表兼容纯空白项，同时继续拒绝非字符串
- 人工反馈Prompt不混入旧Reviewer建议，并包含操作类型和最大数量硬约束
- 模型返回超出人工反馈范围的操作时会被拒绝且不修改State
- 原有人工反馈、需求补充、刷新恢复和双栏页面测试继续通过

本阶段实现规则：

- `duration_seconds`是节点完成后的实测耗时，不是页面实时倒计时
- 页面提示只展示Orchestrator已经决定的动作，不自行复制流程判断
- 表单版本变化只重建页面控件，不改变HumanFeedback领域状态
- LLM只提出结构化修正操作，Python拥有最终数据合并权
- 一组修正操作必须全部通过校验后才能写入State，不允许部分成功

单元测试不访问真实 DeepSeek、Milvus 或 Embedding 服务。

## 当前限制

- Agent 尚不能自主选择 Tool，节点仍由 Python Orchestrator 受控编排
- 单个LLM节点执行期间仍是同步等待，节点完成后才会刷新页面
- 当前显示等待预期和完成后耗时，但没有后台任务、实时进度百分比或取消单个节点的能力
- 浏览器刷新不能中断正在执行的同步LLM请求；页面只阻止同一任务重复启动节点
- 当前任务只保存在Streamlit服务进程内，服务重启后任务会丢失
- MySQL历史任务持久化尚未实现，计划在后续独立阶段设计
- 知识资产上传与持久化尚未设计为独立知识库管理功能
- Milvus 与 Embedding 地址仍在现有客户端中硬编码
- 自动化用例生成和异常日志分析不在当前产品范围
