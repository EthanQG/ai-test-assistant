## 1. 产品背景

### 1.1 核心问题

测试工程师在需求分析阶段需要完成：

- 阅读和理解 PRD
- 提取业务模块、规则、状态和边界
- 识别异常、并发、幂等和容错风险
- 复用历史 Bug 和测试经验
- 将分析结果整理为可执行的测试点

这些工作依赖个人经验，容易出现：

- 需求事实与个人推测混杂
- PRD 信息缺失但未及时提出
- 历史缺陷经验无法稳定复用
- 测试点遗漏关键异常路径
- 生成结果缺少来源和质量检查

### 1.2 产品定位

Test Analysis Agent 是一个面向测试工程师的受控智能需求与测试分析助手。

它不以“替代测试工程师”为目标，而是：

- 将原始需求转换为结构化分析
- 主动识别信息缺口
- 检索并复用历史测试资产
- 生成可审核的结构化测试点
- 自动评审结果并进行有限修正
- 将最终决定权保留给用户

### 1.3 版本演进

V1 将测试点生成、pytest 用例生成和日志分析同时纳入一个固定 Workflow，范围过大且功能完成度不一致。

V2 收敛为一个核心场景：

> 从 PRD 输入到高质量测试分析报告的完整 Agent 闭环。

自动化用例生成和日志分析保留在历史归档中，不属于 V2 当前范围。

## 2. 目标用户

### 2.1 主要用户

| 用户 | 需求 |
|---|---|
| 初级测试工程师 | 学习需求分析方法，减少明显场景遗漏 |
| 测试工程师 | 提升 PRD 分析和测试点整理效率 |
| 测试开发工程师 | 获得结构化测试资产，为后续自动化提供输入 |

### 2.2 用户责任

用户需要：

- 确认 PRD 和上传资料符合数据安全要求
- 回答 Agent 提出的关键待确认项
- 审核模型生成的推导风险和测试点
- 决定最终结果是否可以保存到知识库

Agent 输出是辅助分析结果，不替代产品、研发和测试人员对业务预期的确认。

当前 Streamlit 页面定位为 V1 功能演示界面：优先保证完整功能链路、Agent状态可解释性和
项目演示效果，不要求复刻DeepL，也不承诺生产级响应式布局、后台任务和高可用能力。

## 3. 产品目标与非目标

### 3.1 本期目标

1. 支持文本和常见文档格式的 PRD 输入
2. 将需求转换为结构化事实、规则、状态、风险和待确认项
3. 在信息不足时暂停流程并请求用户补充
4. 从 Milvus 检索相关历史测试资产
5. 生成结构化、可追踪来源的测试点
6. 自动检查测试点的覆盖度、重复项和可执行性
7. 对未达标结果进行有限次数修正
8. 展示 Agent 的步骤、工具调用和降级状态
9. 支持用户修改、导出和确认后知识沉淀
10. 建立离线评测集，量化不同方案的效果

### 3.2 非本期目标

- 生成可直接执行的完整 pytest 测试代码
- 自动执行测试或控制真实测试环境
- 异常日志根因分析
- 多 Agent 自由协作
- 无限制的自主工具调用
- CI/CD 平台集成
- 企业级账号、组织和权限系统
- 生产级高可用承诺
- 在 Agent 核心稳定前进行全面前后端分离
- 将当前 Streamlit V1 演示页面打磨为生产级固定工作台或完整复刻第三方产品界面

## 4. 产品原则

### 4.1 事实优先

业务规则、数值、角色、状态和预期结果必须来自当前需求或用户明确补充，不得将模型推测写成需求事实。

### 4.2 推导可解释

通用测试经验可以用于发现风险，但每条推导风险必须说明依据。

### 4.3 信息不足则询问

缺少确定预期结果所需的信息时，生成待确认项并暂停后续关键步骤，不自行补充业务规则。

### 4.4 历史资产不能覆盖当前需求

RAG 结果只用于提供测试思路和回归风险。历史业务名词、规则和数值不能直接覆盖当前 PRD。

### 4.5 代码控制安全边界

Agent 使用受控编排：

- 合法步骤由代码定义
- 状态转换由代码校验
- 工具使用白名单限制
- 修正次数由代码限制
- 终止状态不能继续执行

### 4.6 人工确认

最终报告保存到历史资产库前必须由用户确认。

## 5. 核心用户流程

```text
用户输入或上传PRD
  → 解析文档
  → RequirementAnalyzer结构化分析
  → 是否存在关键待确认项？
      ├─ 是：等待用户补充，恢复任务
      └─ 否：继续
  → KnowledgeRetriever检索历史资产
  → TestPointGenerator生成结构化测试点
  → Reviewer评审质量
  → 是否达到质量阈值？
      ├─ 否且未达到最大修正次数：Reviser定向修正并重新评审
      ├─ 否且达到最大次数：停止自动循环并等待人工处理
      └─ 是：继续
  → Finalizer生成最终可读报告
  → 用户审核和提交结构化反馈
      ├─ 测试建议：Reviser修正后重新评审
      └─ 业务规则：用户二次确认后写入需求事实并重新修正
  → Finalizer更新最终报告
  → 导出或确认后保存到知识库
```

当前 Streamlit 页面已经接入 Agent 主链路。页面逐次调用Application Service的
`advance_task()`，由Application Service加载任务并让`AgentOrchestrator`决定和执行下一节点；
每个节点完成后保存State、决策和事件。遇到待确认项时暂停，用户补充后仍通过同一边界恢复任务。

## 7. Agent 节点定义

### 7.1 RequirementAnalyzer

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | `state.requirement` |
| 使用能力 | PromptService、LLMService |
| 输出 | 摘要、模块、事实、规则、状态、风险、待确认项 |
| 成功 | 结果通过 JSON 与字段校验并写入 State |
| 分支 | 有待确认项时进入 `waiting_for_user` |
| 失败 | State 进入 `failed`，记录 `TASK_FAILED` |

### 7.2 KnowledgeRetriever

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 结构化需求分析结果 |
| 使用能力 | RAGService |
| 输出 | `rag_context`、`rag_max_score`、`rag_matched_count` |
| 无命中 | 记录 0 条命中并允许继续 |
| 服务失败 | 记录降级原因，当前规则允许任务继续 |

### 7.3 TestPointGenerator

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 需求分析结果、历史资产、用户补充 |
| 使用能力 | PromptService、LLMService |
| 输出 | 结构化测试点集合 |
| 失败 | 不生成不完整的最终报告 |

### 7.4 TestPointReviewer

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 需求分析结果和测试点 |
| 输出 | 评分、缺失场景、重复项、幻觉项和修正建议 |
| 分支 | 达标进入 Finalizer；未达标进入 Reviser |

### 7.5 TestPointReviser

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 当前测试点和 Reviewer 意见 |
| 输出 | 结构化增删改操作；由Python原子合并为定向修正后的测试点 |
| 限制 | 最大迭代次数由代码控制 |

### 7.6 HumanFeedbackHandler

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 用户对测试点的增删改、优先级和补充说明 |
| 输出 | 结构化人工反馈及确认状态 |
| 分支 | 测试建议进入Reviser；业务规则补充先等待明确确认 |

### 7.7 AgentOrchestrator

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 当前 `TestAnalysisState` |
| 输出 | 唯一合法的下一动作及原因 |
| 规则 | Python选择节点，LLM不决定流程分支 |
| 停止 | 等待用户、评审通过、达到修正上限或任务终态 |
| 安全 | 同时限制修正次数和一次运行的最大总步骤数 |

### 7.8 Finalizer

| 项目 | 定义 |
|---|---|
| 状态 | 已实现（Agent 内部） |
| 输入 | 通过评审的结构化测试点、评审结果与执行元数据 |
| 输出 | `final_result`统一结果及可下载Markdown报告 |
| 原则 | Python确定性汇总，不调用LLM，不改变已评审测试点 |
| 限制 | 未评审、评审未通过或存在待处理人工反馈时禁止最终化 |

## 8. AgentState 与执行规则

### 8.1 当前 State

当前已保存：

- 任务 ID、原始需求
- 状态和当前步骤
- 需求摘要
- 模块、需求事实、业务规则和状态流转
- 推导风险和待确认项
- 本地 Bug 知识
- RAG 上下文、最高分和命中数量
- 知识检索状态和降级错误原因
- 结构化测试点集合
- Reviewer 评分、覆盖映射、问题清单、达标状态和阈值
- 修正次数；修正后保留上一轮评审并使旧达标状态失效
- 人工反馈动作、类型、目标、内容、原因、确认和应用状态
- 每轮评审结果、修正前后测试点快照、最大修正次数
- Finalizer统一结果和Markdown报告
- 报告、错误和执行事件
- 创建和更新时间

### 8.2 状态

```text
pending
  → running
      → waiting_for_user
          → running
      → completed
      → failed
```

### 8.3 强制规则

- 空需求不能创建任务
- 只能完成当前步骤
- `waiting_for_user` 必须先恢复才能继续
- `completed` 和 `failed` 不能继续执行
- 空报告不能完成任务
- LLM 结构化输出未通过校验时不能写入后续节点
- Reviewer 修正循环必须设置最大次数

### 8.4 初期编排策略

初期 Orchestrator 使用 Python 规则，不让 LLM 完全自由选择：

```text
没有需求分析结果
→ RequirementAnalyzer

存在待确认项
→ 等待用户

尚未检索知识
→ KnowledgeRetriever

尚未生成测试点
→ TestPointGenerator

尚未评审
→ Reviewer

评分未达标且未达到最大次数
→ Reviser

评分通过且没有待处理人工反馈
→ Finalizer

达到最大修正次数但仍未通过
→ 停止自动循环，等待人工处理
```

后续可以在合法动作白名单内加入 LLM 软判断，但代码仍负责强制安全规则。

## 9. 页面与交互需求

### 9.1 当前页面

当前 Streamlit 页面支持：

- 文本和文档输入
- 左侧需求工作台与右侧任务结果区组成固定工作区，页面外层不随长需求和长结果持续增长
- 左侧只允许需求正文滚动，右侧只允许当前结果正文滚动；状态、阶段和结果导航保持可见
- 左侧主要操作位于正文滚动区之外，等待补充、规则确认、完成和失败状态均无需滚动到正文末尾操作
- 左右主框统一使用560px工作区高度，在未开始、执行中、等待用户和完成状态下底部对齐
- 任务创建后从`state.requirement`稳定展示只读原始需求
- 所有状态共用`main.py`中的宽屏页面容器和唯一产品头部
- 未开始和普通执行状态使用约42/58双栏；完成、修正上限和人工反馈状态使用约33/67双栏
- 每轮最多3个关键待确认问题的回答或“暂不确定”
- 基于`run_next()`的逐节点执行与节点完成后轨迹刷新
- 当前步骤和需求分析、知识检索、生成测试点、评审与修正、整理报告五阶段进度
- 执行中显示原生Spinner、节点中文名称、处理内容、合理等待说明和最近3条关键进展
- 等待用户、达到修正上限、完成和失败状态停止Spinner，不展示虚假百分比或剩余时间
- 五阶段进度使用非交互式轻量标签，避免与可点击按钮混淆
- 执行详情通过Dialog展示Orchestrator决策和完整Agent事件，不再堆叠在结果正文下方
- 测试点列表只展示摘要，前置条件、步骤、预期结果和来源通过独立详情Dialog展示
- 测试点列表每页5条，只展示标题、中文分类、优先级和场景摘要
- 测试点详情默认收起且同时最多展开一条，展开后显示前置条件、步骤、预期结果和来源
- 四个结果导航在普通rerun后保持当前选择，人工反馈提交后仍停留在人工反馈结果
- Tab激活态使用产品蓝色，主区域、按钮和展开项使用一致的6～8px圆角与克制阴影
- 结构化测试点、Reviewer评分与Finalizer报告展示
- 中文步骤和测试点分类标签
- 表格化Markdown报告预览与下载
- 服务进程存活期间基于`task_id`的刷新恢复
- 在右侧“人工反馈”Tab提交结构化人工反馈，不在左侧重复提供入口
- 达到自动修正上限时保留结果，并引导进入“人工反馈”Tab
- 测试建议支持新增、修改、删除和调整优先级
- 业务规则支持独立二次确认或取消
- 人工反馈状态、自动修正次数和人工修正次数分别展示

当前尚不支持：

- MySQL历史任务的页面搜索与列表
- 基于乐观锁、execution_id和执行租约的跨进程重复执行保护
- 单个LLM响应的Token级流式展示
- 当前Agent结果经确认后沉淀为MySQL KnowledgeAsset并建立Milvus索引
- 节点级输入预算、真实Token统计和分层性能事件
- RAG、Reviewer/Reviser和三组方案的离线质量评测

### 9.2 后续页面规划

Streamlit页面作为V1功能演示层冻结。阶段2.12已经完成调用入口替换且未调整布局和CSS；

## 11. 质量评测方案

- 需求事实提取准确率

- 测试点重复率

- 平均 Token 消耗
- 平均修正次数

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| LLM JSON 不稳定 | 节点失败 | 结构化响应、严格校验、错误可见和一次受控重试 |
| 需求信息不足 | 测试点预期错误 | 待确认项与人工补充 |
| RAG 错误召回 | 历史业务污染 | 阈值过滤、来源标记、Reviewer |
| Agent 无限循环 | 成本和响应失控 | 代码编排、最大步骤和迭代次数 |
| 外部服务不可用 | 流程中断 | 明确降级策略和事件 |
| Token 过多 | 成本与延迟升高 | 结构化输入、Top-K、上下文截断 |
| 未确认结果污染知识库 | 后续RAG产生错误业务规则 | Reviewer通过、用户确认、KnowledgeAsset准入和版本停用 |
| MySQL成功但Milvus失败 | 知识资产无法被检索 | pending/index_failed状态、幂等重试和索引事件 |
| 重复请求再次执行节点 | 状态、成本和事件重复 | version、execution_id和执行租约 |
| 项目范围扩张 | 核心功能完成度下降 | 非目标清单和阶段验收 |
| 简历表述超前 | 面试无法自证 | 只描述已实现且有证据的能力 |
